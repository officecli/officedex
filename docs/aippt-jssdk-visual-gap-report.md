# OfficeDex AI PPT 视觉差距分析报告

更新时间：2026-09-14  
适用产品：OfficeDex  
对照对象：[《腾讯内测 Cheso，一个专做 PPT 的 AI Agent，实测有吓到我》](https://mp.weixin.qq.com/s/EzrkDXCRF43-mTJzfh5L5A)  
对照产物：[TikTok运营-自由构图融合版.pptx](../../artifacts/aippt/tiktok-jssdk-free-30/TikTok运营-自由构图融合版.pptx)

## 结论先行

这次差距的主因不是“自由构图不够多”，也不是单纯的配色问题，而是当前生成链路缺少一层**页面艺术指导和视觉资产规划**：

1. Cheso 样例先决定每页要用什么视觉角色（封面主视觉、数据看板、图表、流程图、插画或海报），再安排文字和几何。
2. 我们最近的 30 页已经做到每页独立构图、原生可编辑、机器验收通过，但视觉角色仍以“文字 + 卡片/线条/圆环”为主，图片、插画、图表、数据标注和场景化主视觉明显不足。
3. 因此下一步不是继续增加更多矩形变体，而是把 `visual_role + asset_plan + focal_point + content_budget` 加入生成契约，让 Skill 负责页面家族路由，JSSDK 负责可编辑实现，渲染验收负责检查视觉层级和语义归属。

目标应当是“**受控的自由构图**”：学习模板中的机制和排版规则，但每页依据内容重新选择视觉角色、素材和几何，不套整页模板，也不靠随机扰动制造假多样性。

## 1. 对照样例看到了什么

文章中的样例并非一种固定模板，而是一个能在不同任务间切换的视觉系统。可归纳为五个家族：

| 页面家族 | 参考样例的特征 | 对内容的帮助 |
|---|---|---|
| 技术/品牌封面 | 深墨绿或深色背景、网格纹理、超大标题、短副标题、强烈单一焦点 | 让主题在第一眼成立，建立品牌记忆 |
| 内容总览/技术地图 | 左侧编号清单，右侧网络节点或路线图，底部用数字做证据锚点 | 同时表达章节结构与主题关系 |
| 数据看板/经营分析 | KPI 卡、条形图、折线图、环形图、表格、图例、机会提示 | 把“数据很多”变成可扫描、可比较、可行动 |
| 流程/路线图/产品说明 | 三段或多段流程，箭头、状态、角色和结果卡片组合 | 把动作顺序、责任和结果放在同一视觉语法里 |
| 插画/海报/素材页 | 生成式插画或照片承担主视觉，文字只做标题和少量信息层 | 让抽象主题变成可感知的场景、人物或物件 |

文章还展示了产品层能力：先检索或读取附件，生成 Markdown，再生成 PPT 大纲供确认，之后逐页生成并实时展示；导出 PPTX/PDF 后仍可编辑，还能复制页面做 A/B 对照；文件、图片、模板和版本被放在项目中统一管理。这些能力不等同于“页面变漂亮”，但会直接影响 OfficeDex 的可用体验和迭代效率。

## 2. 我们当前版本的基线

最近的 TikTok 自由构图版本在工程可靠性上已经有一条可复用的基线：

- 30 页、30 个唯一布局标签，相邻页面没有重复。
- 每页从独立 drawer 生成，使用学习到的轨道、环形、分支、时间轴、阶梯、金字塔等机制，而不是整页套模板。
- JSSDK 执行、PPTX 导出、严格回读和渲染检查通过；渲染错误 `0`、文字溢出 `0`、原生图片 `0`。
- 436 个文本体完成 `font_metrics` 覆盖，`skipped=[]`，最终文件保持原生可编辑。
- 第二轮已经修复了正文跑出卡片、标题压轴线、回复阶梯高度不足、中心节点过窄等真实排版问题。

这说明“Skill 选择机制 + JSSDK 绘制 + 机器/人眼复核”的方向是正确的；问题在于这条链路主要保证**结构正确**，还没有把**视觉表现力**设成同等强度的生成约束。

### 图表基线不是空白

这次核对还发现，图表训练资产和渲染基础实际上已经存在：

- `presentation/quality/pptx-gate/fixtures/corpus` 中有 44 组 `chart-*` fixture，覆盖普通/堆积柱条、折线、面积、饼/环、雷达、散点、组合图和部分股票/三维图表。
- [`@learnof/chart`](../../presentation/packages/deps/chart/README.md) 公共包已经拥有图表数据模型、SVG 布局、绘制、序列化和编辑会话，基础类型包括 `column`、`bar`、`line`、`area`、`pie`、`donut`、`radar`、`scatter`。
- [`ChartController`](../../presentation/packages/presentation-engine/src/capabilities/chart/chart-controller.ts) 已有 `insertChart`、`setChartData`、标题、图例、坐标轴、数据标签和样式控制能力。
- [`ShapeCollection`](../../presentation/packages/presentation-office-js/src/objects.ts) 已补上受控的 `addChart` 入口，MOP Host 会写入 `graphicFrame -> chartSpace`；当前生成器仍不能把它当成已验收配方，因为导出、严格回读、renderer 和视觉抽查尚未完成。
- OfficeDex 的 [`VibeChart`](../src/shared/types.ts) 已扩展为多 series、来源、图例/坐标轴选项，并保留旧 `categories + values` 兼容；组合图、堆积、双轴和数据标签仍需继续补齐。
- Skill 的 [`registry.json`](../skills/aippt-jssdk-design/registry.json) 仍把 `chart` 放在 `blocked`，命中后按 [`progressive-loading.md`](../skills/aippt-jssdk-design/references/progressive-loading.md) 进入 `needs_capability_review`；这是一份旧能力快照，不代表当前渲染内核不存在图表能力，但它会让生成路由主动避开图表。

因此，“训练集中有图表，但生成模板里没有图表”的剩余根因是两段链路尚未完成：**Skill 路由仍被 blocked 快照拦截，图表作者 API 还没有导出/回读/视觉证据**；语义模型和最小 JSSDK 写入路径已经开始修复。现在用原生矩形和线条手绘一个“像图表”的页面，最多是视觉占位，不等同于可编辑、可读数、可复用的原生图表。

## 3. 差距矩阵

| 维度 | 参考样例 | 当前 OfficeDex | 影响 | 判断 |
|---|---|---|---|---|
| 视觉资产 | 照片、插画、贴纸、图标、网格、真实图表共同出现 | 以原生文字、矩形、线条、圆环为主，图片和插画很少 | 页面更像“结构稿”，不够像可直接展示的成品 | P0 |
| 页面家族 | 技术封面、数据看板、图表分析、流程、插画海报明显切换 | 结构标签很多，但视觉语汇仍集中在卡片和几何 | 30 页“各不相同”，却没有形成丰富的视觉节奏 | P0 |
| 数据表达 | 条形图、折线图、环形图、表格、图例和机会提示成套出现 | 有指标、阶梯、表格和关系图，但缺少真正的图表系统和数据注释 | 信息密度和可信度不够，难以快速比较 | P0 |
| 主视觉 | 每页有明确 focal point，封面和海报几乎由主视觉承担记忆点 | 多数页面由标题和多个同权重面板共同承担注意力 | 读者不知道先看哪里，页面显得平 | P0 |
| 内容密度 | 标题短、正文少，以图形、标签、数字承担说明 | 文本解释偏多，卡片常承担过多句子 | 需要缩小字号或堆叠组件，排版风险上升 | P1 |
| 色彩节奏 | 深绿、浅灰、奶油色、海报暖色、蓝色模板等按任务切换 | TikTok 版本整体偏深色/米色和墨绿，跨页色彩角色较单一 | 主题家族辨识度不足，视觉疲劳 | P1 |
| 对齐与组件归属 | 标题、图表、卡片、注释有明确网格和边界 | 机器检查能发现越界，但不能完全发现“正文属于错误卡片”等语义错位 | 仍会出现看似通过、实际不专业的页面 | P0 |
| 模板学习 | 既有模板库、可上传模板、缩略图预览和变体选择 | 已能读取来源证据和机制，但模板知识还没有沉淀为家族级设计系统 | 学到的是局部形状，未充分学到字体、间距、图表和资产比例 | P1 |
| 生成体验 | 大纲确认、逐页生成、实时预览、复制页对比、版本管理 | 当前重点在离线生成和最终验证 | 设计反馈来得太晚，修改成本高 | P2 |

## 4. 根因分析

### 4.1 当前多样性主要是“几何多样性”

`free-composition-plan.json` 和 `jssdk-evidence.json` 已经能证明 30 页使用不同的布局与机制。这解决了“同一模板换色”的问题，但没有解决“每页看起来像不同种类的演示文稿”——因为页面仍大多由同一批原生 primitive 组成：标题、正文、卡片、圆、线、标签。

真正可感知的多样性至少需要四个维度同时变化：

```text
几何结构  ×  视觉角色  ×  资产类型  ×  信息密度
```

只改变第一项，结果就是结构签名很丰富，视觉印象仍然相近。

### 4.2 自由构图入口缺少“先选主视觉”的步骤

目前的思路是先根据内容关系选机制，再由 drawer 布局。下一版需要把问题改写成：

```text
本页最重要的认知任务是什么？
读者先看到哪个视觉锚点？
这个锚点是图、数据、场景、物件还是文字？
剩余信息如何围绕锚点落位？
```

没有这一步，生成代码会自然回到最熟悉的卡片和文本框。

### 4.3 排版验收指标和“成品感”不是同一件事

`overflow=0`、`render_errors=0` 和 `font_metrics` 覆盖是必要条件，但它们不能判断：

- 主视觉是否足够大、是否在第一视线位置。
- 标题、数字、图表和说明的权重是否拉开。
- 正文是否放在正确的卡片或语义分区里。
- 图表刻度、图例、标注和结论是否连贯。
- 留白是不是有意的，而不是缺少素材造成的空洞。

所以需要在现有四层验收（文字、几何、语义、视觉）上增加可记录的视觉评分，而不是只保留布尔通过/失败。

### 4.4 模板学习还停留在“形状机制”，没有学完整套设计系统

模板来源应同时蒸馏以下信息：

- 页面家族和使用场景。
- 标题/副标题/正文/脚注的字号比例和字重梯度。
- 网格列数、边距、卡片圆角、阴影和边框角色。
- 图表类型与数据标签规则。
- 图片或插画占页面面积的比例、裁切方式和焦点位置。
- 主题色如何随着页面任务切换，而不是整套 deck 只用一个主色。

只记录 `required_geometry`，会得到“会画这个轮廓”的代码，却得不到参考样例中的成品质感。

## 5. 下一版生成契约

在现有 `layout_spec` 之上，建议为每页加入以下字段。它们应进入 generation plan 和证据文件，不能只写在 prompt 或注释里。

```json
{
  "generation_mode": "hybrid",
  "family": "data_dashboard",
  "variant": "kpi-plus-bar-chart",
  "relation": "comparison",
  "visual_role": "chart",
  "focal_point": { "kind": "chart", "area": "right", "weight": 0.62 },
  "asset_plan": [
    { "kind": "native_chart", "required": true, "editable": true },
    { "kind": "icon", "source": "lucide-or-native", "required": false }
  ],
  "content_budget": { "title_chars": 18, "body_lines": 3, "items": 5 },
  "density": "high",
  "theme_family": "light-navy-orange",
  "required_geometry": ["title", "chart", "legend", "takeaway"],
  "layout_rules": ["12-column-grid", "aligned-baselines", "chart-labels-inside"],
  "qa": ["focal_area", "asset_coverage", "hierarchy_contrast", "semantic_ownership"]
}
```

字段职责如下：

- `visual_role`：规定本页主要靠什么表达，不允许所有页面默认走 text/card。
- `focal_point`：规定第一注意力区域、面积和视觉权重。
- `asset_plan`：在生成前声明需要原生图表、图片、插画、图标还是纯几何；素材不足时要显式降级或阻止生成。
- `content_budget`：先约束标题、正文和条目容量，再决定字号和组件尺寸，避免最后一步硬塞文字。
- `theme_family`：允许按页面家族切换受控主题，保持 deck 一致性而不单调。
- `qa`：把“漂亮”拆成可检查的项目，并保留人工复核结果。

## 6. Skill、JSSDK 和验收各自要增强什么

### Skill 层：负责选择与约束

1. 在解析内容关系后，先路由 `family` 和 `visual_role`，再选择 `source_mechanism`。
2. 对每 5 页至少安排一个不同的视觉家族；相邻页不能只更换颜色或卡片排列。
3. 当内容包含可比较数字、趋势或占比时，优先要求图表/看板；没有真实数据时禁止伪造精确数字。
4. 当主题适合场景、人物、物件或情绪时，要求 `asset_plan` 申请图片/插画素材；素材生成使用 imagegen，不能由几何占位长期代替。
5. 读取模板时同时提取网格、字号梯度、图表规范、图片比例和主题变体，形成家族级 recipe。

### JSSDK 代码层：负责可编辑实现

1. 建立四组可复用但参数化的 drawer：`hero/editorial`、`data/dashboard`、`diagram/process`、`illustration/poster`。
2. 图表优先使用原生可编辑对象；若 JSSDK 没有高阶图表 API，则用轴、柱、折线、环形、图例和数据标签组成可编辑图表 primitive。
3. 图片和插画只占据 `asset_plan` 声明的区域，并保留裁切、圆角、边界和 z-order；不能把整页渲染成一张图片来掩盖排版问题。
4. 每个 drawer 在绘制前执行内容容量计算，至少返回 `required_geometry`、文本框 bounds 和 focal area，供验收使用。
5. 保留 `family` 级的字体、间距和色彩 token，避免每个页面自行猜尺寸。

### 验收层：负责证明“能用且像成品”

在现有文字/几何/语义/视觉四层之外，新增以下量化记录：

| 指标 | 建议口径 |
|---|---|
| `focal_area` | 主视觉占有效画布面积及其是否落在首视线区域 |
| `asset_coverage` | `asset_plan.required` 的素材是否实际出现、类型是否正确 |
| `hierarchy_contrast` | 标题、关键数字、正文、脚注的字号/颜色/面积对比是否达到阈值 |
| `semantic_ownership` | 每个文本和连接线是否落在声明的组件边界内 |
| `whitespace_balance` | 主要留白是否围绕主视觉和阅读路径，而非大块无用途空白 |
| `family_variety` | 一组页面中视觉家族、资产类型和信息密度的分布 |

验收结果建议从布尔值升级为：

```json
{
  "layout_review": "passed",
  "visual_review": "passed_with_notes",
  "scores": {
    "focal_area": 0.82,
    "asset_coverage": 1.0,
    "hierarchy_contrast": 0.76,
    "semantic_ownership": 1.0,
    "whitespace_balance": 0.71
  },
  "human_review_slides": [1, 4, 8, 12, 17, 23, 30]
}
```

任何必需素材缺失、语义归属失败或人工发现“成品感不足”，都应标记 `layout_review_failed` 或 `visual_review_failed`，不能用 `overflow=0` 覆盖。

## 7. 优先级路线图

### P0：下一轮必须做

- 把 `visual_role`、`asset_plan`、`focal_point`、`content_budget` 加入 generation plan 和证据 schema。
- 先实现四个页面家族的 drawer：封面/编辑型、数据看板、图表分析、流程/关系图。
- 将 `VibeChart`/表格数据接入 `addChart`，补齐组合/堆积/双轴等语义，并完成原生 `chartSpace` 的写入、导出、严格回读和渲染验收。
- 建立至少一套可编辑条形图、折线图、环形图、KPI 卡和图例 primitive。
- 用 44 组既有 chart fixture 先做图表作者能力的回归，不要重新手写一套与公共图表包平行的 SVG 图表引擎。
- 只有在作者 API、回读、渲染和视觉抽查通过后，才从 `blocked` 移除 `chart`，注册 `data_dashboard`/`chart_analysis` 配方；解除 blocked 不能先于证据。
- 在生成前输出 4 张试稿（每个家族 1 张），通过人工视觉检查后再扩展整套 deck。
- 把 `semantic_ownership`、`focal_area` 和 `whitespace_balance` 加入渲染验收。

### P1：紧接着做

- 引入 imagegen 资产管线，为需要场景化表达的页面生成图片/插画，并记录提示词、尺寸和版权/来源信息。
- 从模板来源蒸馏字体梯度、网格、图表和图片比例，形成家族级 recipe，而不是只保留轮廓机制。
- 增加内容压缩和拆页策略，优先减少正文句子，不用一味缩小字号。
- 为一套 deck 设定 2～3 个主题变体和密度节奏，避免 30 页都落在同一深色/米色气质里。

### P2：产品体验

- 在 OfficeDex 中展示“资料/Markdown → 大纲 → 4 张试稿 → 全量生成”的阶段状态。
- 支持逐页预览、复制当前页、版本对比和按页重生成，把视觉反馈前移。
- 在项目文件树中管理模板、图片、图表数据、生成证据和最终 PPTX，形成可追溯资产链。

## 8. 对 TikTok 下一版的具体建议

不建议把现有 30 页全部重画成更复杂的卡片。更有效的实验是保留现有内容和 JSSDK 验证框架，重做 8～10 张代表页：

- 1 张强主视觉封面：大标题 + TikTok 场景化图片或插画。
- 2 张数据/增长看板：KPI、趋势图、对比图和结论标注。
- 2 张流程或运营机制页：流程节点配角色、动作和结果，不只用文字框。
- 2 张内容/评论分析页：截图或内容样张 + 标注层 + 结论卡。
- 1 张路线图/团队协作页：时间轴或组织关系配真实图标/头像资产。
- 1～2 张自由实验页：允许海报、拼贴或杂志式构图，验证资产驱动的自由度。

这 8～10 张先通过新的视觉验收，再决定是否扩展到 30 页。成功标准不是“布局标签更多”，而是缩略图一眼能分辨页面家族，同时所有文字、图表、图片和连接关系仍然可编辑、可验证。

## 最终判断

OfficeDex 已经解决了“能生成、能导出、页面不溢出、每页不是同一模板”的第一阶段问题。与参考样例相比，第二阶段要补的是**视觉角色路由、真实资产/图表、主视觉聚焦、家族级设计系统和成品级验收**。

这也是对现有方法文档的直接增补：Skill 继续负责模式和机制选择，JSSDK 继续负责具体绘制，但两者之间必须增加一份可验证的页面艺术指导。只要这层契约建立起来，模板学习、自由构图和排版准确性才能同时向前，而不是互相牺牲。
