OfficeDex 1.0.23：重复问题根因与修复证据

2026-10-10 · 对照 1.0.15 / 18 / 19 / 20 / 21 / 22 / 23 七份用户报告及实际代码、报告内嵌文件

结论：存在同类问题反复出现。其中单附件未写回与 1.0.19 批量问题同源；当前文档另建属于路由同类缺陷的新触发条件；⌘S 属于此前未覆盖的输入路径。现有证据更支持“修复与验收只覆盖部分路径”，不能笼统归因于 1.0.23 又改坏了。

上次把局部路径通过当成整类问题关闭，修复范围与结论不匹配。尤其一条名为“Full access 直接写入”的旧测试，只检查没有 suggestion，未检查保存调用或源文件。它实际上允许“既没写回，也没 Review 入口”通过。此处是实现和测试共同漏检，不能归咎于验收报告。

1. 本次三项问题的直接原因

问题已核实的因果链与历史的关系
N23-01
单附件原件未改，副本没有入口		后台 modify 生成 .modified.docx，不会自动覆盖原件。服务仅在 reviewRequested || batchItem 时登记源文件与提案，单文件 Full access 被漏掉，也没有调用 ApplyArtifactSuggestion。任务直接取 worker 的 completed。结果卡又只查当前 library 的 artifactTaskId，未使用任务自带产物路径，导致磁盘已有副本却显示“没有新文件”。确定同源复现：N19-02 曾在批量路径发现完全相同的“副本完成≠原件应用”。1.0.20 对应提交 cac874c 只补了 batchItem 条件，没有覆盖单附件。1.0.15 AG01 的入口问题也是同一交付链上的历史现象，但不能据此认定所有历史现象代码根因完全相同。
N23-02
修改当前 DOCX 被当成新建		requestsNewFile 对整段文本匹配 create/generate 等动词。报告待替换的原句恰为 OD23 Agent can create a document.，其中“create a document”触发新建。原文数据被当成控制指令，绕开当前文档编辑器，模型随后生成了一份审阅说明文档。此外本地编辑与后台服务各自维护 Review 正则，报告中的“先展示 Review…等待确认，不要自动应用”未被完整覆盖。同类路由缺陷的新触发条件：N15-02 是“明确新建却编辑历史文件”，N21-01 是“活动文档覆盖明确附件”；这次方向相反，由引用正文触发。不能把三者写成同一个补丁回退，也不能归因于模型偶然发挥。
N23-03
PPT ⌘S 未保存，按钮可保存		快捷键只绑定父 window。PPT 标题、备注位于 iframe 中，键盘事件不跨 frame 冒泡。capture=true 只能捕获同一文档内的事件。顶部 Save 在父窗口，能走正确保存链，因此出现按钮成功、按键无效。此前遗漏的路径：历史保存、恢复、冲突测试不能代替 iframe 内真实按键。已在 Chromium 中重现旧监听方式收到 0 次保存事件，并验证修复后的标题、备注、父页面及 iframe 重载/嵌套行为。

2. 为什么“上次没有，这次又有”

  • 测试入口不同。单/双附件、引用文件、活动编辑器、历史产物的分支不同；Review 与 Full access 的提交语义也不同。1.0.20 的引用文件 Review 成功，不能证明 1.0.23 的独立单附件 Full access 成功。
  • “未复现”不等于根因已消除。N18-03 的先询问格式问题在 1.0.19 未复现，1.0.20 N20-01 又出现。不同措辞命中了不同的启发式规则。
  • 恢复位置不同。1.0.19 长 PPT 测的是 0/24 Stop→Resume，报告明确未覆盖部分页完成后恢复。1.0.21 的 13/24 恢复暴露空白正文；1.0.22 又发现句号、重复正文、额外内容。只验页数/文件存在，不能代替逐页内容约束。
  • 后两份是“只列问题”的报告。1.0.22 未列单附件和快捷键，不代表这些路径已测且通过。不能由某个问题没有出现于报告，倒推出上一版本没有该漏洞。
  • 版本增量证据不支持简单回归叙事。officedex 的 1.0.23 提交 d0780b3 只改三个版本文件；officecli 47b7705 改 PPT 精确内容校验。此次定位的 DOCX 路由、写回和父窗口快捷键代码并非在该提交新增。打包环境差异不能仅凭源码排除，但当前已有确定的旧代码漏洞。

4. 已落地的修复

  1. 统一后台修改的交付状态。所有 modify 保存 source 与 artifact。单文件 Full access 在真实 ApplyArtifactSuggestion 成功后才完成，保存期间不放行后续队列；失败保留提案、错误和副本入口。批量仍按已有约定交付可审阅提案。显式 Review 等待 Apply。补齐完成事件早于 modify 返回、重启恢复、无产物完成等情况；重启不静默重放自动写入。
  2. 结果不再依赖文件列表是否已加载。AgentTask 携带真实产物路径，未进入当前 library 的副本仍可打开；源文件未出现在列表时仍显示 Review 入口。
  3. 分离字面正文并统一 Review 规则。新建/格式推断先屏蔽引号、代码块等正文载荷，保留原提示传给执行器；本地编辑器和后台服务使用相同 Review 判断。覆盖中文、英文、不同引号以及真正的新建请求。
  4. 保存快捷键穿过实际文档边界。监听同源嵌入编辑器文档，处理挂载、导航、嵌套与卸载；调用与 Save 按钮相同的保存入口，避免编辑器重复处理。当前生产内置编辑器同源；跨域外部编辑器不在此监听器覆盖范围。
  5. 把历史回归接入本地 macOS 构建。新增 npm run test:acceptance:regressions，新构建在编译前强制运行 lint 和该套件；失败即退出。已编译产物的 --skip-build 重打包不重跑源码测试。CONTRIBUTING 明确“未复现”和“已修复”的证据边界。

6. 仍须保留的证据边界

当前是源码修复与自动化回归通过，尚未重新签名构建、发布或完成 macOS 原生客户端复测，不能标为客户端验收关闭。仓库缺少用户指定的 scripts/devctl，未绕开协调要求启动开发服务器。浏览器测试使用隔离页面，无长期服务。

报告另提到两次单附件 Review 显示 Couldn’t finish，但内嵌证据没有给出这两次的完整后台错误。现有证据不能把它们都归因于未写回或引号误路由，更不能保证模型/文件解析失败已消除。后续原生复测必须收集对应 taskId 与错误，并确认真实 Before/After。1.0.23 未复测通过的长 PPT、自然失败队列等历史问题，也不能因本次三个修复而一并关闭。

原生关闭标准：同一签名 ARM64 包中重跑报告原始请求；单附件 Full access 读回源 DOCX 必须为 final；Review 确认前原件哈希不变，Apply 后目标变更、Undo 后恢复；标题和备注焦点下按 ⌘S 后重开 PPTX 确认磁盘内容，并覆盖拒绝写入时仍显示失败。记录应用版本、构建 commit、任务 ID 与源/结果哈希。
